1. Le développeur fait partie du code : Il n'existe pas de développement objectif. Le logiciel n'est pas un outil, mais l'empreinte binaire de l'état mental, de la tension artérielle et de la colère du programmeur ce jour-là.

2. Le chaos est sacré : Si un algorithme est trop transparent, c'est suspect. Le véritable code gonzo est comme une jungle : dangereux, sombre, et seul son créateur sait où se trouvent les pièges.

3. Tester sur le serveur de production : Les tests unitaires sont le sport des lâches et des bureaucrates. Le véritable programmeur gonzo débogue directement en production, au milieu des cris des utilisateurs.

4. La documentation est une fiction : Les commentaires ajoutés au code ne sont pas des explications, mais des monologues intérieurs, des manifestes politiques ou des appels au secours. Celui qui ne comprend pas le code n'est pas digne de l'utiliser.

5. Le pointeur (pointer) est le maître : Utilise un langage de programmation qui ne te limite pas ! La gestion directe de la mémoire est le gage de ta liberté. L'utilisation de types sûrs n'est qu'une entrave. Utilise les adresses mémoire comme s'il n'y avait pas de lendemain. La Memory Leak est ton cri que personne n'entend.

6. Architecture fondée sur la caféine : La qualité du code est directement proportionnelle à la quantité de stimulants consommés et inversement proportionnelle au nombre d'heures passées à dormir.

7. Le message d'erreur comme art : Le message d'erreur ne doit pas aider, mais choquer. L'utilisateur doit ressentir le mépris de la machine et de son créateur à chaque Runtime Error.

8. Ne nettoie jamais (Refactor) : Ce que tu as écrit une fois en état de transe est sacré. Si tu y touches pour le rendre « plus beau », tu tues l'âme du logiciel.

9. La date limite n'est qu'une suggestion : Le programmeur gonzo ne travaille pas à l'heure, il chevauche les vagues de l'inspiration et de la panique. Le code est terminé lorsque le développeur s'effondre.

10. Le logiciel doit être imprévisible : Un bon programme gonzo contient toujours un peu d'aléatoire. Si chaque pression sur un bouton produit la même chose, c'est un produit industriel ennuyeux, pas de l'art.

11. La responsabilité ? Exclue : Le contrat de licence doit tenir en un seul point : « S'il démarre, c'est ton problème. » Le développeur n'est pas Dieu, seulement un témoin de la destruction de la machine.

12. La stratégie de sortie : Lorsque le projet s'effondre, ne t'explique pas. Efface l'historique Git, brûle le disque dur et trouve au Mexique un endroit sans réseau mobile.
